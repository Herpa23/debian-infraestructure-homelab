

## 1. Configuración del Servidor NFS

### A. Instalación de Paquetes
En la máquina virtual `debian-infra`, se verificó e instaló el demonio del servidor NFS:

```bash
sudo apt update
sudo apt install nfs-kernel-server -y
```

### B. Creación y Estructura del Directorio Compartido

Se creó un directorio dedicado dentro de `/srv` (reservado para servicios de datos) para alojar los archivos que se expondrán en la red:

Bash

```
sudo mkdir -p /srv/nfs/shared
sudo chown -R root:nogroup /srv/nfs/shared
sudo chmod 2755 /srv/nfs/shared
```

Explicación del 2 dentro de los permisos:

El cuarto dígito a la izquierda (`2`) activa el bit **SetGID (Set Group ID)** en el directorio. En entornos de almacenamiento en red (como NFS), esto ofrece ventajas críticas:

1. **Heredación Automática de Grupo:** Por defecto, cualquier archivo creado en Linux adopta como grupo el del usuario creador. Con SetGID activo, **todos los archivos y subdirectorios nuevos heredan automáticamente el grupo propietario del directorio padre** (`root:nogroup` o el grupo asignado al recurso).
    
2. **Colaboración sin Fricción:** Evita bloqueos de permisos cruzados entre distintos usuarios o procesos que accedan al repositorio compartido, permitiendo una lectura y escritura fluida sin requerir intervención administrativa constante.


_(Nota: Se asigna temporalmente al usuario `root:nogroup` o se ajustan permisos específicos para evitar restricciones de acceso anónimo/remoto)._

### C. Configuración de Exportaciones (`/etc/exports`)

Se especificaron las reglas de compartición editando el archivo de configuración del servidor NFS:

Bash

```
sudo nano /etc/exports
```

Se añadió la siguiente línea para permitir acceso exclusivo a la subred del homelab:

Plaintext

```
/srv/nfs/shared 192.168.56.0/24(rw,sync,no_subtree_check,no_root_squash)
```

- **`rw`**: Permite permisos de lectura y escritura.
    
- **`sync`**: Sincroniza las escrituras en disco de manera inmediata para garantizar la integridad de los datos.
    
- **`no_subtree_check`**: Desactiva la verificación de subárboles, mejorando la fiabilidad y velocidad de transferencia.
    
- **`no_root_squash`**: Permite que el usuario `root` del cliente mantenga sus privilegios sobre el recurso compartido (útil en entornos controlados de laboratorio).
    

### D. Aplicación y Activación del Servicio

Para aplicar los cambios y exportar los directorios configurados sin reiniciar el sistema, se ejecutó:

Bash

```
sudo exportfs -av
sudo systemctl enable nfs-server
```

## 2. Apertura de Puertos en UFW para NFS (Mediante Perfiles de Aplicación)

Para evitar la apertura manual de puertos numéricos individuales y aprovechar las abstracciones nativas del sistema, se configuró el cortafuegos utilizando el perfil de aplicación que provee el paquete NFS. 

### A. Comando de Aplicación de Regla
Para restringir el acceso exclusivamente desde la subred del homelab hacia la IP del servidor utilizando el perfil integrado, se ejecutó:

```bash
sudo ufw allow in from 192.168.56.0/24 to 192.168.56.10 app nfs
````

### B. Verificación del Estado del Firewall

Al consultar el estado detallado de UFW (`sudo ufw status verbose`), el sistema interpreta el perfil y despliega explícitamente los puertos y protocolos asociados:

Plaintext

```
192.168.56.10 111,2049/tcp (NFS) ALLOW IN    192.168.56.0/24    
192.168.56.10 111,2049/udp (NFS) ALLOW IN    192.168.56.0/24 
```

### ¿Por qué se hace de esta forma y cuáles son sus ventajas?

1. **Abstracción y Mantenimiento a Futuro:** Los paquetes Debian registran perfiles de aplicaciones estandarizados en `/etc/ufw/applications.d/`. Si en futuras versiones del sistema operativo el servicio NFS requiriera puertos auxiliares adicionales o sufriera modificaciones, el perfil oficial se encarga de actualizar los mapeos necesarios sin que tengas que reescribir reglas manuales de puertos.
    
2. **Legibilidad y Auditoría Profesional:** Al auditar el cortafuegos con `sudo ufw status verbose`, la regla se muestra etiquetada claramente bajo el nombre **`(NFS)`** junto a sus respectivos puertos y protocolos. Esto facilita enormemente la lectura en auditorías de seguridad, evitando tener que adivinar para qué servicio se abrieron los puertos `111` o `2049`.
    
3. **Reducción del Error Humano:** Especificar números de puerto a mano (`111,2049`) combinando TCP y UDP en una misma línea es propenso a errores de sintaxis o a descuidar alguno de los protocolos auxiliares que `rpcbind` y `mountd` necesitan para operar de forma estable. El perfil encapsula toda esa complejidad en una sola palabra (`app nfs`).

### E. Creación del Grupo Dedicado y Asignación de Pymes (`nfs-users`)
Para mantener un control granular de los usuarios que tienen permitido interactuar lógicamente con los archivos del recurso compartido, se creó un grupo específico en el servidor (`nfs-users`) y se asoció al directorio: 1. **Creación del grupo en el servidor:**

```bash
sudo groupadd nfs-users
```


- **Asignación del grupo al directorio compartido:**
    
    ```bash
    sudo chown -R root:nfs-users /srv/nfs/shared
    ```
    
- **Incorporación de usuarios al grupo:** Para que un usuario del sistema tenga derechos de acceso e interacción, debe ser añadido al grupo correspondiente:

    ```bash
    sudo usermod -aG nfs-users hporras
    ```


## 3. Configuración del Cliente NFS (Cómo acceder al recurso)

Una vez que el servidor Debian (`192.168.56.10`) exporta el directorio, el equipo cliente debe montar dicho recurso en su propio sistema de archivos local.

### A. Instalación de Utilidades NFS en el Cliente

En la máquina cliente (por ejemplo, tu equipo host o una terminal Linux de prueba), asegúrate de tener instalado el paquete cliente de NFS:

Bash

```
sudo apt update
sudo apt install nfs-common -y
```

### B. Creación del Punto de Montaje Local

Crea un directorio local en el cliente donde se proyectará el almacenamiento remoto:

```bash
sudo mkdir -p /mnt/homelab-nfs
sudo chown $USER:$USER /mnt/homelab-nfs
```

### C. Montaje Manual del Recurso Compartido

Para montar de forma inmediata la carpeta compartida utilizando el protocolo NFS:

```bash
sudo mount -t nfs 192.168.56.10:/srv/nfs/shared /mnt/homelab-nfs
```

### D. Verificación del Montaje Exitoso

Para comprobar que el recurso remoto está correctamente enlazado y accesible, ejecuta:

```bash
df -h | grep "nfs"
```

O bien, lista el contenido del directorio montado:

```bash
ls -la /mnt/homelab-nfs
```

### E. Montaje Persistente mediante `/etc/fstab` (Opcional)

Si deseas que el cliente monte automáticamente el recurso compartido cada vez que se encienda o reinicie el equipo, edita el archivo de tablas de sistemas de archivos en el cliente:

```bash
sudo nano /etc/fstab
```

Dentro del archivo de texto nos ubicamos en el fondo donde se va a añadir la siguiente línea de configuración 

```
192.168.56.10:/srv/nfs/shared  /mnt/homelab-nfs  nfs  defaults,noexec,nosuid,nodev,_netdev  0  0
```

#### Desglose de Opciones de Seguridad y Red (`/etc/fstab`):

- **`defaults`**: Aplica las opciones predeterminadas de montaje (`rw`, `suid`, `dev`, `exec`, `auto`, `nouser`, `async`).
    
- **`noexec`**: Impide la ejecución directa de binarios o scripts dentro del recurso compartido (hardening a nivel de montaje).
    
- **`nosuid`**: Bloquea la interpretación de los bits Set-UID y Set-GID en ejecutables remotos para prevenir escaladas indebidas de privilegios.
    
- **`nodev`**: Inhabilita la interpretación de dispositivos de bloques o caracteres en el directorio montado.
    
- **`_netdev`**: **Obligatorio para montajes de red**. Le indica a `systemd` que posponga el montaje automático hasta que las interfaces de red del cliente estén completamente activas, evitando colapsos o _timeouts_ durante el booteo.

-  Nota sobre el `fsck` ultima unidad: Los ceros finales indican al sistema que no debe realizar respaldos automáticos ni comprobaciones de integridad con `fsck` al arrancar, ya que se trata de un sistema de archivos de red remoto y no de un disco local.

### F. Aplicación y Verificación Final del Montaje Una vez guardado
el archivo `/etc/fstab`, se deben ejecutar los siguientes comandos de validación en el cliente: 

1. **Forzar la recarga y montaje de los sistemas de archivos definidos en fstab:** 

 ```bash
   sudo mount -a
```

(Nota: Este comando lee el archivo `/etc/fstab` y monta cualquier recurso pendiente que no estuviera activo. Si no devuelve ningún mensaje de error en la terminal, significa que la sintaxis de la línea es completamente correcta).

2. **Verificar el montaje activo y la disponibilidad de lectura/escritura:**

    ```bash
    df -h | grep nfs
    ls -la /mnt/homelab-nfs
    ```

3. **Prueba de escritura colaborativa:** Para comprobar que el bit SetGID y los permisos del servidor funcionan como se espera, puedes crear un archivo de prueba desde el cliente:

    ```bash
    touch /mnt/homelab-nfs/test-conexión.txt
    ls -la /mnt/homelab-nfs/
    ```


Si el archivo se crea de manera exitosa y hereda la pertenencia al grupo propietario configurado en el servidor, el almacenamiento compartido en red está **plenamente operativo, seguro y listo para su uso**.
