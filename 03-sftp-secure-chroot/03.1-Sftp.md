
# Módulo 03: Servidor SFTP Seguro con Aislamiento Chroot 

Este documento detalla la implementación de un servidor **SFTP (SSH File Transfer Protocol)** seguro en la máquina virtual `debian-infra`, aplicando la técnica de **Chroot Jail** (jaula de cambios de raíz). El objetivo es permitir transferencias de archivos cifradas bloqueando al usuario exclusivamente dentro de su directorio designado, impidiendo cualquier acceso al sistema de archivos global del servidor.

---

## 1. Concepto y Arquitectura de Seguridad (Chroot) 

Por defecto, cuando un usuario se conecta mediante SSH o SFTP, tiene visibilidad de todo el árbol de directorios del sistema operativo (limitado únicamente por sus permisos de lectura/escritura). El aislamiento **Chroot** modifica la raíz percibida (`/`) para ese usuario específico, haciendo que su directorio asignado actúe como si fuera la raíz absoluta del disco. 
### Requisito Crítico de OpenSSH para Chroot: 

El subsistema SFTP con Chroot exige una regla de arquitectura estricta: * **La carpeta raíz de la jaula (`ChrootDirectory`) debe pertenecer estrictamente al usuario `root`** y tener permisos donde el usuario enjaulado **no tenga privilegios de escritura**. 

* Para permitir que el usuario suba archivos, se debe crear un subdirectorio interno dentro de esa jaula que sí pertenezca al usuario. 

--- 
## 2. Creación del Grupo y Estructura de Directorios

Para mantener un orden administrativo limpio, se gestionará el acceso mediante un grupo dedicado. 
### A. Creación del Grupo de SFTP 

```bash 
sudo groupadd sftp-users
```


### B. Creación de la Estructura de Directorios para la Jaula

Se creará una ruta base que servirá como jaula estricta y un subdirectorio interno para el almacenamiento de archivos:

```bash
sudo mkdir -p /srv/sftp/usuario_sftp/shared
```

### C. Asignación Estricta de Propietarios y Permisos (Hardening)

Cumpliendo con los requisitos de seguridad de OpenSSH:

1. **La carpeta raíz de la jaula (`/srv/sftp/usuario_sftp`) debe ser propiedad de `root` y sin permisos de escritura para otros:**

    ```bash 
    sudo chown root:root /srv/sftp/usuario_sftp
    sudo chmod 755 /srv/sftp/usuario_sftp
    ```

2. **El subdirectorio interno (`shared`) debe pertenecer al usuario o grupo para permitir la transferencia de datos:**

    ```bash
    sudo chown root:sftp-users /srv/sftp/usuario_sftp/shared
    sudo chmod 775 /srv/sftp/usuario_sftp/shared
    ```

## 3. Creación y Configuración del Usuario SFTP

Se creará un usuario dedicado exclusivamente a la transferencia de archivos, aplicando las mismas buenas prácticas de aislamiento que en Samba.

1. **Creación del usuario:**

    ```bash
    sudo useradd -m -g sftp-users -s /sbin/nologin sftpuser
    ```
    
    - `-m`: Crea un directorio home temporal (que luego reorientaremos o ignoraremos).
        
    - `-g sftp-users`: Asigna al usuario directamente al grupo de seguridad SFTP.
        
    - `-s /sbin/nologin`: Bloquea completamente el acceso a una terminal interactiva o por SSH tradicional.

2. **Asignación de contraseña:**

    ``` bash
    sudo passwd sftpuser
    ```


## 4. Centralización y Gestión de Llaves Públicas (Ed25519)

Para evitar problemas de permisos en la jaula y mantener una gestión limpia, las llaves públicas de autenticación se almacenarán en un directorio protegido del sistema.

### A. Creación del Directorio Centralizado en el Servidor

Bash

```
sudo mkdir -p /etc/ssh/sftp_keys
sudo chmod 755 /etc/ssh/sftp_keys
sudo chown root:root /etc/ssh/sftp_keys
```

### B. Generación y Configuración de la Llave en el Cliente

Desde el equipo cliente (host), genera tu par de llaves dedicadas (si no dispones de una específica):

Bash

```
ssh-keygen -t ed25519 -C "sftp-user-homelab"
```

_(Guárdala por ejemplo como `~/.ssh/id_ed25519_sftp`)_.

Copia el contenido de la llave pública (`id_ed25519_sftp.pub`) y guárdalo en el servidor dentro de un archivo cuyo nombre coincida exactamente con el usuario (`sftpuser`):

```bash
sudo nano /etc/ssh/sftp_keys/sftpuser
```

Pega el contenido y guarda el archivo.

### C. Aplicación de Permisos Estrictos a la Llave

OpenSSH descartará la llave si los permisos o el propietario no son seguros:

```bash
sudo chown root:root /etc/ssh/sftp_keys/sftpuser
sudo chmod 644 /etc/ssh/sftp_keys/sftpuser
```

## 5. Configuración del Servidor SSH (`/etc/ssh/sshd_config`)

Se actualizará el demonio SSH para aplicar el aislamiento Chroot y enlazar la llave autorizada mediante variables dinámicas.

1. **Editar el archivo de configuración:**

    ```bash
    sudo nano /etc/ssh/sshd_config
    ```
    
2. **Añadir el bloque condicional al final del archivo:**
    
    ```
    Match Group sftp-users
        ChrootDirectory /srv/sftp/%u
        ForceCommand internal-sftp
        X11Forwarding no
        AllowTcpForwarding no
        AuthorizedKeysFile /etc/ssh/sftp_keys/%u
    ```

### Desglose de Parámetros:

- **`Match Group sftp-users`**: Aplica las reglas únicamente a los miembros del grupo.
    
- **`ChrootDirectory /srv/sftp/%u`**: Encierra al usuario en su jaula usando la variable `%u` (nombre de usuario dinámico).
    
- **`ForceCommand internal-sftp`**: Fuerza el uso exclusivo del subsistema SFTP interno, bloqueando comandos de shell.
    
- **`AuthorizedKeysFile /etc/ssh/sftp_keys/%u`**: Define la ruta centralizada y protegida donde se buscará la llave pública correspondiente al usuario.


## 6. Validación y Aplicación de Cambios

1. **Verificación de sintaxis del servicio SSH:**

    ```bash
    sudo sshd -t
    ```
    
    _(Si no arroja errores, la sintaxis es correcta)._
    
2. **Reinicio del servicio:**

    ```bash
    sudo systemctl restart ssh
    ```
    

## 7. Pruebas de Conexión y Validación 
### A. Simplificación de la Conexión mediante `~/.ssh/config` (Cliente) 

Para evitar tener que escribir parámetros largos en cada conexión (como la IP, el usuario y la ruta de la llave privada), se recomienda configurar un alias en el archivo de configuración SSH del equipo cliente. 1. **Editar o crear el archivo de configuración en el cliente (`~/.ssh/config`):**

```bash 
 nano ~/.ssh/config
```

- **Añadir el siguiente bloque de host dedicado:**

    ```
    Host homelab-sftp
        HostName 192.168.56.10
        User sftpuser
        Port 22
        IdentityFile ~/.ssh/id_ed25519_sftp
    ```
    
    (Nota: Asegúrate de que el archivo tenga permisos seguros en el cliente ejecutando `chmod 600 ~/.ssh/config`).
    
- **Conexión simplificada:** Gracias a este alias, ahora puedes conectarte de forma directa y limpia ejecutando simplemente:

    ```bash
    sftp homelab-sftp
    ```


## B.**Diagnóstico de Errores con Modo Verbose (`-v`)

Si al intentar conectar surge algún error de autenticación (por ejemplo, rechazo de la llave o problemas con los permisos del servidor), puedes añadir la bandera de depuración `-v` (o `-vvv` para nivel máximo de detalle) para ver exactamente qué está fallando en el intercambio criptográfico:

```bash
sftp -v homelab-sftp
```

_(Esto desplegará en pantalla el registro paso a paso de la negociación SSH, permitiéndote identificar si el servidor rechazó la llave por permisos incorrectos o si hubo un fallo en la ruta)._

### B. Verificación del Aislamiento (Chroot Jail)

Una vez dentro de la consola interactiva `sftp>`:

1. Comprueba que el directorio raíz está limitado:
    
    Plaintext
    
    ```
    sftp> pwd
    sftp> cd ..
    sftp> pwd
    ```
    
    _(El resultado debe confinar al usuario sin permitirle salir al árbol global del sistema)._
    
2. Ingresa al directorio de subidas y prueba transferir un archivo:
    
    Plaintext
    
    ```
    sftp> cd shared
    sftp> put archivo_local.txt
    ```
    

### C. Verificación de Bloqueo de Shell

Cualquier intento de abrir una sesión interactiva por SSH tradicional fallará de inmediato debido a la directiva `/sbin/nologin`:

Bash

```
ssh sftpuser@192.168.56.10
```
