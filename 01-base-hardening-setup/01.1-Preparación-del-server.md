
# Módulo 01: Instalación Base, Particionado y Hardening en Debian 12

Este módulo documenta el proceso de despliegue desde cero de la máquina virtual `debian-infra`, abarcando el diseño de almacenamiento lógico, la puesta a punto de red, la configuración inicial del sistema y las políticas estrictas de endurecimiento de sistemas (hardening).

---

## 1. Diseño de Arquitectura y Particionado
Durante la instalación de Debian 12 (Netinst), se configuró un esquema de particionamiento lógico personalizado para asegurar la estabilidad del sistema y evitar cortes o saturaciones por desbordamiento de servicios:

- **`/` (Root):** Partición principal para los binarios del sistema operativo y dependencias críticas.
- **`/var`:** Partición separada para alojar registros (`/var/log`) y colas de servicios, previniendo que un crecimiento desmedido de logs sature el almacenamiento general del sistema.
- **`/home` y directorios de datos (`/srv`):** Espacio reservado para perfiles de usuario, llaves y puntos de montaje de almacenamiento externo.
- **`swap`:** Espacio de intercambio optimizado para la gestión de memoria virtual de la VM.

### 3. Configuración y Activación de la Interfaz LAN Modular En instalaciones mínimas de Debian (Netinst)
La interfaz de red dedicada a la red interna o Host-Only no se levanta automáticamente por defecto tras el booteo del sistema. Para asegurar la persistencia y el levantamiento de la IP estática sin sobrecargar el archivo principal de configuración, se implementó una estructura modular dentro del directorio `/etc/network/interfaces.d/`.
#### A. Identificación del Nombre de la Interfaz
Se listaron las interfaces de red disponibles en el sistema para ubicar el identificador correspondiente a la red interna (distinto a la interfaz de loopback `lo`): 

```bash
ip a
```
(Nota: Se identificó el nombre asignado, por ejemplo, `enp0s8` o `enp0s3`).

#### B. Creación del Archivo de Configuración Modular

Se creó y editó un archivo dedicado para la interfaz dentro de la ruta modular del sistema:

```bash
sudo nano /etc/network/interfaces.d/enp0s8
```

Se añadió la siguiente declaración para configurar de forma estática la dirección IP del laboratorio:

```
auto enp0s8
iface enp0s8 inet static
    address 192.168.56.10
    netmask 255.255.255.0
```


#### C. Activación Manual y Persistencia del Servicio de Red

Para forzar el inicio inmediato de la interfaz y asegurar que el demonio de red aplique los cambios correctamente de forma persistente, se ejecutó:

``` bash
ifup enp0s8
systemctl restart networking
```

NOTA: Tienes que encontrarse dentro del sistema el paquete **ifupdown**, si no es así, no vas a poder realizar esta acción. Ejecuta este comando para poder instalarlo:

```bash
apt install ifupdown -y
```

#### D.Verificación de Conectividad Local
Para comprobar que la interfaz levantó de manera exitosa y posee la dirección IP asignada, se consultó nuevamente el estado de las interfaces:

Bash

```bash
ip a
```


## 4. Creación de Usuario No-Root y Configuración de Sudo
Al realizar una instalación mínima de Debian 12 (Netinst), el sistema operativo por defecto no incluye configurados usuarios administradores adicionales ni la herramienta de escalamiento de privilegios `sudo`. Trabajar cotidianamente como usuario `root` representa un riesgo crítico de seguridad, por lo que se procedió a crear un usuario dedicado y configurar sus permisos. 
### A. Verificación e Instalación de Sudo
Antes de configurar privilegios administrativos, se verificó si el paquete `sudo` se encontraba disponible en el sistema: 

```bash 
command -v sudo
```

Si el comando no retorna ninguna ruta, se procede a instalarlo elevando temporalmente los privilegios como root, si seguimos en un usuario root:


```bash
apt update && apt install sudo -y
```

### B. Creación del Usuario Administrador (`hporras`)

Se creó un nuevo usuario llamado `hporras` asignándole su respectiva contraseña y directorio personal:


```bash
adduser -m -s /bin/bash hporras
```

_(Durante el asistente, se completaron los datos solicitados por el sistema y se definió una contraseña robusta)._

### C. Asignación de Permisos de Administrador (Grupo Sudo)

Para permitir que el nuevo usuario pueda ejecutar comandos administrativos mediante `sudo`, se lo incorporó al grupo correspondiente:


```bash
usermod -aG sudo hporras
```

### D. Validación de Permisos

Para comprobar que la configuración se aplicó correctamente, se cambió de sesión al usuario creado y se validó la ejecución de comandos con privilegios elevados:

```bash
su - hporras
sudo whoami
```
## 5. Generación de Llaves Criptográficas (SSH Keypair)

Desde la terminal del equipo cliente, se generó el par de claves RSA/Ed25519 para el acceso administrativo seguro sin contraseñas:


```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_25519_debianinfra
ssh-copy-id -i ~/.ssh/id_25519_debianinfra.pub hporras@192.168.56.10
```

## 6.  Archivo ~/.ssh/config
### ¿Cómo se implementa?

1. En tu máquina cliente (fuera de la VM, en tu terminal habitual), creá o editá el archivo de configuración dentro de la carpeta oculta `.ssh`:
    
    
    ```bash
    nano ~/.ssh/config
    ```
    
2. Se creo el siguiente contenido adaptado al laboratorio:
    
    
    ```
    Host debian-infra
        HostName 192.168.56.10
        User hporras
        Port 22
        IdentityFile ~/.ssh/id_25519_debianinfra
    ```
    
3. Guardá los cambios (`Ctrl + O`, luego `Enter`) y salí (`Ctrl + X`).
    
4. Asegurate de darle los permisos de seguridad correctos (es un requisito estricto de SSH para que las llaves privadas no queden expuestas):
    
    
    ```bash
    chmod 600 ~/.ssh/config
    ```


## 7. Endurecimiento Estricto del Servicio SSH (`/etc/ssh/sshd_config`)

Una vez validados los accesos por claves, se modificaron los parámetros críticos de seguridad en el demonio SSH aplicando las siguientes directivas:

- **`PermitRootLogin no`** -> Prohíbe el acceso directo del usuario root por red.
    
- **`PubkeyAuthentication yes`** -> Fuerza el uso exclusivo de autenticación por llaves públicas criptográficas.
    
- **`PasswordAuthentication no`** -> Desactiva por completo el acceso mediante contraseñas tradicionales.
    
- **`PermitEmptyPasswords no`** -> Impide autenticaciones con claves vacías o nulas.
    
- **`X11Forwarding no`** -> Bloquea el reenvío de X11 para reducir la superficie de ataque gráfico en el servidor.

## 8. Configuración de Políticas de Firewall (UFW)

Para blindar el servidor frente a accesos no autorizados, se implementó un esquema de filtrado de paquetes mediante **UFW (Uncomplicated Firewall)**, siguiendo el principio de mínima exposición.

### A. Políticas Base (Default Policies)
Se configuró el comportamiento predeterminado del cortafuegos:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
```

- **`deny incoming`**: Bloquea todo el tráfico entrante por defecto. Ningún puerto está accesible al exterior salvo que se cree una regla explícita de `ALLOW`.

- **`allow outgoing`**: Permite las conexiones salientes iniciadas por el propio servidor, facilitando tareas legítimas de actualización del sistema y sincronización de red.


### B. Aplicación de Reglas Específicas del Módulo 01

Para este nivel inicial, se habilitó exclusivamente el acceso administrativo remoto vía SSH restringido al cliente del laboratorio:

```bash
sudo ufw allow in from 192.168.56.1 to 192.168.56.10 port 22 proto tcp
```

### C. Verificación del Estado del Firewall

Para comprobar que las políticas y reglas se aplicaron correctamente de forma persistente, se auditó el estado detallado del servicio:

```bash
sudo ufw status verbose
```

**Salida de referencia esperada en el laboratorio:**

```

Logging: on (low)
Default: deny (incoming), allow (outgoing), disabled (routed)
New profiles: skip

To                         Action      From
--                         ------      ----
192.168.56.10 22/tcp       ALLOW IN    192.168.56.1    
```

## 9. Control de Acceso con AppArmor

Para elevar la postura de seguridad del sistema operativo más allá de los permisos tradicionales de Linux (usuarios, grupos y bits de lectura/escritura/ejecución), se verificó y mantuvo activo el subsistema **AppArmor**.

### A. ¿Para qué sirve AppArmor?
AppArmor es un **MAC (Mandatory Access Control)** integrado directamente en el núcleo (kernel) de Linux. AppArmor determina **qué operaciones exactas puede realizar un proceso específico**, incluso si ese proceso se ejecuta con privilegios elevados (como `root`). Esto se logra mediante perfiles de confinamiento que restringen capacidades como la lectura de archivos sensibles, la apertura de sockets de red o la ejecución de binarios no autorizados.

### B. ¿Por qué se deja activo por defecto en el servidor?
- **Defensa en profundidad:** Funciona como una barrera defensiva secundaria (capa de aislamiento). Si un servicio de red (como SSH o un demonio futuro) sufriera una vulnerabilidad de ejecución remota de código (RCE), el atacante se encontraría confinado estrictamente por las políticas de AppArmor, impidiéndole comprometer el resto del sistema operativo.
- **Protección nativa sin fricción:** Debian 12 instala y configura perfiles predeterminados para los servicios críticos del sistema de forma nativa.

### C. Verificación del Estado del Servicio
Para comprobar que AppArmor se encuentra cargado en el kernel y operando en modo activo de cumplimiento (*enforce*), se ejecutó el siguiente comando de auditoría:

```bash
sudo aa-status
```

**Salida de referencia esperada en el laboratorio:**

```
apparmor module is loaded.
14 profiles are loaded.
14 profiles are in enforce mode.
 0 profiles are in complain mode.
 0 processes have profiles defined.
 0 processes are in unconfined mode.
```

## 10. Protección contra Ataques de Fuerza Bruta (`Fail2ban`)

Para mitigar los intentos automatizados de acceso malicioso e intromisiones por fuerza bruta en los servicios expuestos, se instaló y configuró el demonio **Fail2ban**.

### A. ¿Para qué sirve Fail2ban y por qué se utiliza un archivo `.local`?
- **¿Qué hace?:** Monitorea de forma continua los archivos de registro (*logs*) del sistema en busca de patrones repetitivos de fallos de autenticación. Cuando una dirección IP supera un umbral determinado de intentos fallidos, Fail2ban aplica automáticamente una regla temporal en el firewall (UFW/iptables) para bloquear las conexiones procedentes de dicha IP.
- **¿Por qué usar `jail.local`?:** En las buenas prácticas de administración de sistemas, nunca se modifican directamente los archivos de configuración originales provistos por los paquetes (`jail.conf`). Esto se debe a que las futuras actualizaciones de seguridad o parches del sistema operativo pueden sobrescribir o pisar dichos archivos. Al crear un archivo independiente llamado **`jail.local`**, el sistema prioriza esta configuración personalizada y garantiza la persistencia de las reglas ante actualizaciones de software.

### B. Configuración Implementada (`/etc/fail2ban/jail.local`)
Se definieron políticas estrictas globales (`[DEFAULT]`) y se habilitó específicamente el monitoreo para el servicio de acceso remoto seguro (`[sshd]`):

```text
[DEFAULT]

maxretry  = 3
findtime  = 10m
bantime   = 3600
ignore ip = 192.168.56.1


[sshd]

enabled = true
port    = ssh
backend = systemd
```

### C. Desglose de Parámetros Configurados:

- **`maxretry = 3`**: Establece el número máximo de intentos fallidos permitidos antes de aplicar el baneo (en este caso, 3 intentos).

- **`findtime = 10m`**: Define la ventana de tiempo (10 minutos) en la cual deben acumularse esos intentos fallidos para que se dispare el bloqueo.

- **`bantime = 3600`**: El tiempo (en segundos, equivalente a 1 hora) que la dirección IP permanecerá bloqueada e inhabilitada para conectarse al servidor. Este se puede modificar a lo que quiere un administrar como ejemplo también colocar `bantime = 1d (ban de 1 día)`.

- **`ignoreip = 192.168.56.1`**: Excluye explícitamente a la dirección IP del host físico de cualquier posibilidad de baneo por error operativo.

- **`backend = systemd`**: Le indica a Fail2ban que consulte directamente el journal de systemd para una lectura más eficiente y moderna de los registros de autenticación en Debian 12.


### D. Verificación del Servicio

Para comprobar que el demonio se encuentra activo y monitoreando correctamente la jaula de SSH, se validó el estado del servicio:

```bash
sudo systemctl status fail2ban
```

### E. Verificación del Estado de la Jaula (`fail2ban-client`)
Además de comprobar el estado general del demonio en el sistema operativo, para auditar en tiempo real qué jaulas están activas y cuántas IPs se encuentran bloqueadas actualmente, se utiliza la herramienta nativa de gestión:
```bash
sudo fail2ban-client status sshd
````

**Salida de referencia esperada en el laboratorio:**

```
Status for the jail: sshd
|- Filter
|  |- Currently failed: 0
|  |- Total failed:     0
|  `- File list:        /var/log/auth.log (or systemd journal)
`- Actions
   |- Currently banned: 0
   |- Total banned:     0
   `- Banned IP list: 
```

### F. Interpretación de la salida de `fail2ban-client status sshd`
El reporte generado por la herramienta detalla métricas clave sobre el monitoreo de seguridad, divididas en dos grandes bloques:

1. **Sección de Filtro (`Filter`):**
   - **`Currently failed`**: Número actual de intentos fallidos registrados dentro de la ventana de tiempo activa (`findtime`) que aún no han alcanzado el límite para disparar un baneo.
   - **`Total failed`**: Cantidad acumulada total de intentos fallidos detectados desde que se inició el servicio.
   - **`File list`**: Origen de los datos analizados (en este caso, el journal de systemd o el archivo de log correspondiente).

2. **Sección de Acciones (`Actions`):**
   - **`Currently banned`**: Cantidad exacta de direcciones IP que se encuentran bloqueadas y con el acceso denegado en este preciso momento.
   - **`Total banned`**: Número histórico acumulado de IPs que han sido sancionadas con bloqueos temporales desde el inicio de la ejecución del demonio.
   - **`Banned IP list`**: Listado explícito de las direcciones IP que sufren la penalización de bloqueo vigente en el firewall.
